# Data model

The complete model, module by module. Every table states its columns, its keys and its constraints.
Anything that is not obvious carries the reason underneath it.

This replaces the earlier wave, which described thirty minute blocks and an issued certificate. Both
changed in the domain flows session: see `../domain/01-event-storming.md`.

---

## Rules that apply everywhere

**Tenant.** Every table carries `tenant_id varchar(32) NOT NULL` holding the university code, and
every query filters by it. Four tables are exceptions and say so: `identity.tenants`,
`identity.platform_admins`, `skills.catalog_items` when the item is global, and
`skills.categories`.

**Row level security (TS01).** Every table with `tenant_id` has row level security enabled and one
policy, `tenant_isolation`: a row is visible and writable only when `tenant_id` equals
`app.tenant_id`, which the application sets per transaction (`SET LOCAL`). Exempt, as ADR 0007
decides: `identity.tenants`, `identity.platform_admins`, `identity.access_links` and
`identity.user_sessions`. `skills.catalog_items` also accepts its global rows (`tenant_id IS
NULL`) from any university, and `notifications.notifications` its rows without a university only
from a transaction without one. A new table with `tenant_id` creates its policy in the same
migration. The application connects as a role without `BYPASSRLS` (`ayni_app`); the migrations run
as the owner. `reputation.rating_tags` has no `tenant_id` and no policy: it is reached through its
rating.

`identity.access_links` and `identity.user_sessions` have a nullable `tenant_id`: it is NULL when the
row belongs to a platform administrator, who has no university.

**Keys.** `uuid`, generated by the application.

**No foreign keys across schemas.** A reference to another module's data is a plain `uuid`. Inside a
schema, foreign keys are declared normally.

**Time.** `timestamptz` in UTC. Plain dates where there is no time.

**Enumerations** are `varchar` with a `CHECK`, not Postgres enum types.

**Audit columns.** `created_at` everywhere; `updated_at` where rows change.

**One credit equals one hour.** Blocks are one hour long.

## `identity`

Who everyone is, which university they belong to, and what that university decides for itself.

### `identity.tenants`

Not tenant scoped: it defines them.

```
id                       uuid          PK
code                     varchar(32)   NOT NULL UNIQUE     -- UPC, travels in every request
name                     varchar(160)  NOT NULL
logo_url                 varchar(512)
primary_color            varchar(16)
secondary_color          varchar(16)
email_domains            text[]        NOT NULL DEFAULT '{}'
minimum_teaching_grade   numeric(4,2)  NOT NULL
timezone                 varchar(64)   NOT NULL DEFAULT 'America/Lima'
status                   varchar(16)   NOT NULL            -- ACTIVE | SUSPENDED
created_at               timestamptz   NOT NULL DEFAULT now()
updated_at               timestamptz   NOT NULL DEFAULT now()

CHECK (status IN ('ACTIVE','SUSPENDED'))
INDEX  USING gin (email_domains)
```

`email_domains` is how a person is routed to their university before they have an account.
`timezone` matters because every block is stored in UTC and shown in the university's local time.

### `identity.platform_admins`

Not tenant scoped, by definition: this is the only role that crosses universities, and the one that
must never read academic data.

```
id           uuid          PK
email        varchar(160)  NOT NULL UNIQUE
full_name    varchar(160)  NOT NULL
status       varchar(16)   NOT NULL        -- ACTIVE | DISABLED
created_at   timestamptz   NOT NULL DEFAULT now()
```

Kept apart from `users` on purpose. If administrators lived in the same table as students, every
query over students would have to remember to exclude them, and the privacy boundary would depend on
a `WHERE` clause.

An administrator signs in by link (TS03): an `ACTIVE` row is what makes `POST
/api/v1/access/request` issue a link with no university for its address. A `DISABLED` one is routed
like any other address, and its open sessions stop working.

### `identity.users`

Students and coordinators. Both belong to exactly one university.

```
id                  uuid          PK
tenant_id           varchar(32)   NOT NULL
role                varchar(16)   NOT NULL    -- STUDENT | COORDINATOR
email               varchar(160)  NOT NULL
student_code        varchar(32)               -- NULL for coordinators
full_name           varchar(160)  NOT NULL
career              varchar(160)
current_term        varchar(16)
photo_url           varchar(512)
bio                 varchar(500)
status              varchar(16)   NOT NULL    -- PENDING | ACTIVE | RESTRICTED
onboarding_step     varchar(32)               -- NULL once finished
activated_at        timestamptz
created_at          timestamptz   NOT NULL DEFAULT now()
updated_at          timestamptz   NOT NULL DEFAULT now()

UNIQUE (tenant_id, email)
UNIQUE (tenant_id, student_code)
CHECK  (role IN ('STUDENT','COORDINATOR'))
CHECK  (status IN ('PENDING','ACTIVE','RESTRICTED'))
CHECK  (role = 'COORDINATOR' OR student_code IS NOT NULL)
```

No password column: there are no passwords in this product. `full_name`, `career` and `current_term`
come from the academic system and are not editable in Ayni.

### `identity.access_links`

The magic link. One row per request, single use.

```
id             uuid          PK
tenant_id      varchar(32)               -- NULL for a platform administrator
email          varchar(160)  NOT NULL
purpose        varchar(24)   NOT NULL    -- ACTIVATION | LOGIN | COORDINATOR_INVITE
token_hash     varchar(64)   NOT NULL UNIQUE
expires_at     timestamptz   NOT NULL
consumed_at    timestamptz
requested_ip   varchar(45)
created_at     timestamptz   NOT NULL DEFAULT now()

INDEX (email, purpose) WHERE consumed_at IS NULL
```

The token is stored **hashed**. A leaked database must not hand anybody a working key to every
mailbox. It expires in minutes and is invalidated on use; the session it creates is what lasts.

### `identity.user_sessions`

```
id            uuid          PK
tenant_id     varchar(32)
user_id       uuid                      -- NULL when it belongs to an administrator
admin_id      uuid
token_hash    varchar(64)   NOT NULL UNIQUE
expires_at    timestamptz   NOT NULL
revoked_at    timestamptz
created_at    timestamptz   NOT NULL DEFAULT now()

CHECK (num_nonnulls(user_id, admin_id) = 1)
```

Long lived on purpose: if the session were short, every day would start by waiting for an email.

Every request after TS03 reads one row of this table by `token_hash` (the `UNIQUE` index) to know
who it is. A session opens nothing once `revoked_at` is set, by signing out, or from the
`expires_at` instant on. A student's or a coordinator's carries `tenant_id` and `user_id`; a
platform administrator's carries `admin_id` and no `tenant_id`.

### `identity.academic_records`

What the academic system says the student approved. A copy, refreshed, never edited here.

```
id            uuid          PK
tenant_id     varchar(32)   NOT NULL
user_id       uuid          NOT NULL REFERENCES identity.users(id)
course_code   varchar(32)   NOT NULL
course_name   varchar(160)  NOT NULL
grade         numeric(4,2)  NOT NULL
term          varchar(16)   NOT NULL
synced_at     timestamptz   NOT NULL DEFAULT now()

UNIQUE (tenant_id, user_id, course_code, term)
INDEX  (tenant_id, user_id)
```

### `identity.credit_policies`

What a university gives its students, and for how long it lasts.

```
id                  uuid          PK
tenant_id           varchar(32)   NOT NULL
kind                varchar(16)   NOT NULL   -- BASELINE | TARGETED
credits_amount      integer       NOT NULL
validity_days       integer       NOT NULL   -- how long the granted credits last
target_rule         jsonb                    -- who qualifies, NULL for BASELINE
valid_from          date          NOT NULL
superseded_at       timestamptz
created_by_admin    uuid
created_by_user     uuid
created_at          timestamptz   NOT NULL DEFAULT now()

CHECK (kind IN ('BASELINE','TARGETED'))
CHECK (credits_amount > 0 AND validity_days > 0)
CHECK (num_nonnulls(created_by_admin, created_by_user) = 1)
INDEX (tenant_id, kind) WHERE superseded_at IS NULL
```

`validity_days` replaces any notion of an academic term. Expiry is a date computed when the credits
are granted, so a student can use the platform during holidays without losing what they were given.

A policy is never updated: the old row gets `superseded_at` and a new one is inserted. The
administrator creates the first one when opening the university; the coordinator supersedes it
later. That is why the author can be either.

## `skills`

The catalogue and who is allowed to teach what.

### `skills.categories`

Global. Technology, university courses, languages, design.

```
id           uuid          PK
name         varchar(80)   NOT NULL UNIQUE
sort_order   smallint      NOT NULL DEFAULT 0
```

### `skills.catalog_items`

One table for two kinds of thing, told apart by `scope`.

```
id             uuid          PK
scope          varchar(16)   NOT NULL    -- GLOBAL | UNIVERSITY
tenant_id      varchar(32)               -- NULL when GLOBAL
category_id    uuid          NOT NULL REFERENCES skills.categories(id)
name           varchar(160)  NOT NULL
description    varchar(500)
course_code    varchar(32)               -- only for UNIVERSITY items
status         varchar(16)   NOT NULL    -- ACTIVE | RETIRED
created_at     timestamptz   NOT NULL DEFAULT now()

CHECK  (scope IN ('GLOBAL','UNIVERSITY'))
CHECK  ((scope = 'GLOBAL') = (tenant_id IS NULL))
CHECK  (scope = 'GLOBAL' OR course_code IS NOT NULL)
UNIQUE (tenant_id, course_code)
INDEX  (tenant_id, status)
```

Tools ship with Ayni and are the same everywhere; courses belong to the university that teaches
them. A student sees the global items plus their own university's, which is one condition in the
query and not two tables to join.

The third `CHECK` is what keeps a global item from ever being assigned to a university, which would
quietly make it invisible to everyone else.

### `skills.offered_skills`

What a tutor is enabled to teach.

```
id                  uuid          PK
tenant_id           varchar(32)   NOT NULL
tutor_id            uuid          NOT NULL
catalog_item_id     uuid          NOT NULL REFERENCES skills.catalog_items(id)
status              varchar(16)   NOT NULL   -- PENDING | ENABLED | REJECTED | WITHDRAWN
accreditation_path  varchar(24)              -- ACADEMIC_RECORD | REVIEWED_EVIDENCE
accredited_grade    numeric(4,2)             -- the grade that enabled it, when applicable
enabled_at          timestamptz
created_at          timestamptz   NOT NULL DEFAULT now()
updated_at          timestamptz   NOT NULL DEFAULT now()

UNIQUE (tenant_id, tutor_id, catalog_item_id)
CHECK  (status IN ('PENDING','ENABLED','REJECTED','WITHDRAWN'))
CHECK  (status <> 'ENABLED' OR accreditation_path IS NOT NULL)
INDEX  (tenant_id, catalog_item_id) WHERE status = 'ENABLED'
```

A university course reaches `ENABLED` on its own when the grade clears the threshold. A global tool
can only reach it through reviewed evidence, because no academic record can vouch for it.

`accredited_grade` is copied rather than looked up: the threshold may change later, and what
justified the decision at the time must remain readable.

### `skills.validation_requests`

```
id                  uuid          PK
tenant_id           varchar(32)   NOT NULL
offered_skill_id    uuid          NOT NULL REFERENCES skills.offered_skills(id)
student_note        varchar(1000)
status              varchar(16)   NOT NULL   -- SUBMITTED | APPROVED | REJECTED
reviewed_by         uuid                     -- a coordinator of the same university
reviewed_at         timestamptz
decision_reason     varchar(500)
created_at          timestamptz   NOT NULL DEFAULT now()

CHECK (status IN ('SUBMITTED','APPROVED','REJECTED'))
CHECK (status = 'SUBMITTED' OR (reviewed_by IS NOT NULL AND reviewed_at IS NOT NULL))
INDEX (tenant_id, status) WHERE status = 'SUBMITTED'
```

### `skills.evidence_files`

```
id                     uuid          PK
tenant_id              varchar(32)   NOT NULL
validation_request_id  uuid          NOT NULL REFERENCES skills.validation_requests(id)
file_name              varchar(255)  NOT NULL
storage_key            varchar(512)  NOT NULL
content_type           varchar(100)  NOT NULL
size_bytes             bigint        NOT NULL
uploaded_at            timestamptz   NOT NULL DEFAULT now()
```

The file itself lives in object storage; the database keeps the pointer.

### `skills.learning_interests`

What a student wants to receive, which drives the recommendations on the portal.

```
id                uuid          PK
tenant_id         varchar(32)   NOT NULL
student_id        uuid          NOT NULL
catalog_item_id   uuid          NOT NULL REFERENCES skills.catalog_items(id)
created_at        timestamptz   NOT NULL DEFAULT now()

UNIQUE (tenant_id, student_id, catalog_item_id)
```

### `skills.taught_sessions`

The sessions that were taught on each catalogue item, so a moderator can review the catalogue by use
(US44). A projection of `SessionCompleted`, written only by that listener.

```
session_id       uuid          PK
tenant_id        varchar(32)   NOT NULL
catalog_item_id  uuid          NOT NULL
tutor_id         uuid          NOT NULL
completed_at     timestamptz   NOT NULL

INDEX (tenant_id, catalog_item_id)
```

Keyed by the session, so an announcement delivered twice counts once. `catalog_item_id` has no
foreign key: the row records what another module announced, and a listener that failed on an item it
does not know would leave the announcement unprocessed. Skills keeps it because it
cannot ask reputation, which has `sessions_taught`: reputation already depends on skills. The count
is read and moved by university, like every other table: a coordinator reviews, and joins, the
use of an item in their own university, a global tool included, and never sees another's. It
starts empty, so the sessions completed before it existed are not counted.

### `skills.academic_settings`

What a university decides about its courses (US51). Today only the minimum grade a student needs in a
course to teach it. One row per university, created the first time a coordinator sets it.

```
tenant_id               varchar(32)   PK
minimum_teaching_grade  numeric(4,2)  NOT NULL CHECK (0 to 20)
updated_by              uuid          NOT NULL
updated_at              timestamptz   NOT NULL
```

A university with no row keeps the `identity.tenants.minimum_teaching_grade` it was registered with:
skills reads the row first and falls back to identity, so the two never disagree about which grade is
in force. Changing it never touches an offer already enabled, which keeps the grade it was enabled with
in `offered_skills.accredited_grade`.

### `skills.skill_proposals`

A tool a student asks to add to the catalogue because it is not there (US42). A moderator resolves
it later (US43), one of three ways: approving it creates a catalogue item, merging joins it to an
item the catalogue already has, and rejecting it leaves a reason the student reads.

```
id               uuid          PK
tenant_id        varchar(32)   NOT NULL
proposed_by      uuid          NOT NULL
category_id      uuid          NOT NULL REFERENCES skills.categories(id)
name             varchar(160)  NOT NULL
description      varchar(500)
status           varchar(16)   NOT NULL   -- PROPOSED | APPROVED | MERGED | REJECTED
resolved_by      uuid                     -- the moderator, a coordinator of the same university
resolved_at      timestamptz
decision_reason  varchar(500)
catalog_item_id  uuid          REFERENCES skills.catalog_items(id)   -- the item it ended up in
created_at       timestamptz   NOT NULL DEFAULT now()

CHECK  (status IN ('PROPOSED','APPROVED','MERGED','REJECTED'))
CHECK  (status = 'PROPOSED' OR (resolved_by IS NOT NULL AND resolved_at IS NOT NULL))
CHECK  (status NOT IN ('APPROVED','MERGED') OR catalog_item_id IS NOT NULL)
CHECK  (status <> 'REJECTED' OR decision_reason IS NOT NULL)
UNIQUE (tenant_id, proposed_by, lower(name)) WHERE status = 'PROPOSED'
INDEX  (tenant_id, created_at) WHERE status = 'PROPOSED'
INDEX  (tenant_id, resolved_at DESC) WHERE status <> 'PROPOSED'
```

A proposal is decided once, like a validation request, and the row keeps who decided, when and how:
that is the history a moderator reads. `catalog_item_id` is the item an approval created or the
existing one a merge joined; the student reads it to offer the skill. The unique index only holds
while the proposal waits, so a student whose proposal was rejected can propose the name again.

## `booking`

When a tutor is free, and the reservations over that time.

### `booking.availability_patterns`

```
id               uuid          PK
tenant_id        varchar(32)   NOT NULL
tutor_id         uuid          NOT NULL
day_of_week      smallint      NOT NULL   -- 1 = Monday
starts_at_time   time          NOT NULL
ends_at_time     time          NOT NULL
valid_from       date          NOT NULL
valid_until      date
created_at       timestamptz   NOT NULL DEFAULT now()

CHECK (day_of_week BETWEEN 1 AND 7)
CHECK (ends_at_time > starts_at_time)
INDEX (tenant_id, tutor_id)
```

Availability belongs to the tutor, never to a skill. Being free on Monday at five means being free:
any enabled skill can be taught in that hour.

### `booking.availability_exceptions`

```
id               uuid          PK
tenant_id        varchar(32)   NOT NULL
tutor_id         uuid          NOT NULL
exception_date   date          NOT NULL
starts_at_time   time
ends_at_time     time
kind             varchar(8)    NOT NULL   -- ADD | REMOVE
created_at       timestamptz   NOT NULL DEFAULT now()

CHECK (kind IN ('ADD','REMOVE'))
INDEX (tenant_id, tutor_id, exception_date)
```

A `REMOVE` without times covers the whole day.

### `booking.availability_pauses`

```
id          uuid          PK
tenant_id   varchar(32)   NOT NULL
tutor_id    uuid          NOT NULL
starts_on   date          NOT NULL
ends_on     date          NOT NULL
created_at  timestamptz   NOT NULL DEFAULT now()

CHECK (ends_on >= starts_on)
```

### `booking.hour_blocks`

The generated units of one hour. This is what a search returns and what a booking takes.

```
id            uuid          PK
tenant_id     varchar(32)   NOT NULL
tutor_id      uuid          NOT NULL
starts_at     timestamptz   NOT NULL
ends_at       timestamptz   NOT NULL
status        varchar(16)   NOT NULL   -- AVAILABLE | HELD | BOOKED | RELEASED | WITHDRAWN
held_by       uuid                     -- student holding it, while status = HELD
held_until    timestamptz              -- when the hold expires, while status = HELD
booking_id    uuid                     -- set while BOOKED
pattern_id    uuid          REFERENCES booking.availability_patterns(id)
version       bigint        NOT NULL DEFAULT 0
created_at    timestamptz   NOT NULL DEFAULT now()

UNIQUE (tenant_id, tutor_id, starts_at)
CHECK  (status IN ('AVAILABLE','HELD','BOOKED','RELEASED','WITHDRAWN'))
CHECK  ((status = 'BOOKED') = (booking_id IS NOT NULL))
CHECK  ((status = 'HELD') = (held_until IS NOT NULL AND held_by IS NOT NULL))
INDEX  (tenant_id, starts_at) WHERE status = 'AVAILABLE'
INDEX  (held_until) WHERE status = 'HELD'
```

`UNIQUE (tenant_id, tutor_id, starts_at)` stops a tutor from being in two places at once. `version`
is the optimistic lock: when two students confirm the same hour at the same moment, one update finds
a changed version and loses. Map it with `@Version`.

**The hold.** Choosing an hour takes it out of circulation before the student confirms, so that
nobody else can take it while they are writing what they need help with. The block moves to `HELD`
with the student who holds it and a deadline, and confirming turns it into `BOOKED`.

Without this, two students can be filling in the same confirmation screen and one of them loses the
booking after having written everything, which is the worst possible moment to find out.

A scheduled job returns expired holds to `AVAILABLE`. It runs outside any request, so it has no
tenant of its own: it iterates the universities and wraps each turn in `TenantContext.runAs`. The
partial index on `held_until` is what keeps that job cheap.

`RELEASED` marks an hour freed by cancelling its booking and is not automatically offered again.
`WITHDRAWN` marks an hour removed by an availability change; it can return to `AVAILABLE` when the
tutor's current availability rules include it again.

### `booking.bookings`

A booking covers one or more **consecutive** hours with the same tutor.

```
id                  uuid          PK
tenant_id           varchar(32)   NOT NULL
student_id          uuid          NOT NULL
tutor_id            uuid          NOT NULL
catalog_item_id     uuid          NOT NULL
starts_at           timestamptz   NOT NULL
ends_at             timestamptz   NOT NULL
hours               smallint      NOT NULL
credits_charged     integer       NOT NULL
need_description    text          NOT NULL
status              varchar(16)   NOT NULL   -- CONFIRMED | CANCELLED | COMPLETED | NO_SHOW
cancelled_by        varchar(16)              -- STUDENT | TUTOR | SYSTEM
cancelled_at        timestamptz
cancelled_late      boolean                  -- within 12 hours of the start
cancellation_reason varchar(500)
created_at          timestamptz   NOT NULL DEFAULT now()
updated_at          timestamptz   NOT NULL DEFAULT now()

CHECK (status IN ('CONFIRMED','CANCELLED','COMPLETED','NO_SHOW'))
CHECK (hours >= 1 AND credits_charged = hours)
CHECK (ends_at > starts_at)
CHECK (status <> 'CANCELLED' OR (cancelled_by IS NOT NULL AND cancelled_at IS NOT NULL))
INDEX (tenant_id, student_id, starts_at DESC)
INDEX (tenant_id, tutor_id, starts_at DESC)
```

`credits_charged = hours` is the pricing rule written as a constraint: one credit, one hour.

A cancellation refunds the student, except when the student themselves cancels inside the twelve
hour window. `cancelled_late` records whether it happened inside that window, and `cancelled_by`
who did it: a tutor's cancellation refunds at any hour. A tutor who removes availability over a
confirmed booking is cancelling that session, and it is recorded against them.

`NO_SHOW` is the state of a booking whose session was abandoned ten minutes after its start because
a participant had not joined (US06, US09). It is set whoever was missing; what changes is the
refund and the tutor's record, below.

### `booking.tutor_reliability`

What a tutor's record looks like, kept as facts rather than as a score.

```
id             uuid          PK
tenant_id      varchar(32)   NOT NULL
tutor_id       uuid          NOT NULL
booking_id     uuid          NOT NULL REFERENCES booking.bookings(id)
kind           varchar(24)   NOT NULL   -- LATE_CANCELLATION | NO_SHOW
occurred_at    timestamptz   NOT NULL DEFAULT now()

UNIQUE (booking_id, kind)
INDEX  (tenant_id, tutor_id)
```

One row per incident, never a counter. A counter loses the story and cannot be audited.

`LATE_CANCELLATION` is written when a tutor confirms a cancellation inside twelve hours of the
start. `NO_SHOW` is written when the tutor did not join a session ten minutes after its start **and
the student did**; when both were absent, or only the student, nobody was wronged and no row is
written. The unique key makes either one a single fact however many times the event that causes it
is delivered.

## `sessions`

The live meeting and the evidence that it really happened.

### `sessions.sessions`

```
id                  uuid          PK
tenant_id           varchar(32)   NOT NULL
booking_id          uuid          NOT NULL UNIQUE
student_id          uuid          NOT NULL
tutor_id            uuid          NOT NULL
scheduled_start     timestamptz   NOT NULL
scheduled_end       timestamptz   NOT NULL
room_name           varchar(120)  NOT NULL UNIQUE
started_at          timestamptz
ended_at            timestamptz
status              varchar(24)   NOT NULL   -- SCHEDULED | IN_PROGRESS | COMPLETED |
                                             -- UNVERIFIED | ABANDONED | CANCELLED
created_at          timestamptz   NOT NULL DEFAULT now()

CHECK (status IN ('SCHEDULED','IN_PROGRESS','COMPLETED','UNVERIFIED','ABANDONED','CANCELLED'))
INDEX (tenant_id, scheduled_start)
```

`room_name` is the identifier handed to the video service, unguessable so that a stranger holding a
link cannot walk in.

`UNVERIFIED` is the state of a session that took place but failed the presence check below.
`started_at` is the moment the second participant checked in, so a session that is still
`SCHEDULED`, or that was `ABANDONED`, has none (US09). Entering the room does not start a session:
it starts when both participants entered before ten minutes had passed since its scheduled start.
`ABANDONED` is the state of a session in which either participant, the tutor, the student or both,
had not entered by then (US06, US09); `ended_at` is the moment it was abandoned. It is never given
presence codes and never becomes `UNVERIFIED`.
`CANCELLED` is the state of a session whose booking was cancelled before it started, so that the
history shows what happened instead of an empty workspace (US12).

### `sessions.participations`

```
id                    uuid          PK
tenant_id             varchar(32)   NOT NULL
session_id            uuid          NOT NULL REFERENCES sessions.sessions(id)
user_id               uuid          NOT NULL
role                  varchar(8)    NOT NULL   -- STUDENT | TUTOR
joined_at             timestamptz
left_at               timestamptz
connected_seconds     integer       NOT NULL DEFAULT 0
end_confirmed_at      timestamptz

UNIQUE (session_id, user_id)
CHECK  (role IN ('STUDENT','TUTOR'))
```

`joined_at` is the participant's first arrival and is never moved: coming back after a dropped
connection does not change it (US09). Both participants can read both arrivals. Nothing in the
application writes it twice; the database does not prevent an `UPDATE` made straight on the table.

`connected_seconds` is what the real duration is measured against, and one of the signals the audit
looks at.

`end_confirmed_at` is when the participant confirmed the session was over (US11). The session closes
when both have, or on its own fifteen minutes after the booked hour, and this column is the record of
who confirmed. It is not `left_at`: leaving the call is measured, confirming the end is declared.

### `sessions.presence_checks`

The five minute code. This is the anti fraud mechanism.

```
id             uuid          PK
tenant_id      varchar(32)   NOT NULL
session_id     uuid          NOT NULL REFERENCES sessions.sessions(id)
user_id        uuid          NOT NULL
code_hash      varchar(64)   NOT NULL
issued_at      timestamptz   NOT NULL DEFAULT now()
expires_at     timestamptz   NOT NULL
confirmed_at   timestamptz
attempts       smallint      NOT NULL DEFAULT 0

UNIQUE (session_id, user_id)
CHECK  (attempts <= 5)
```

Five minutes after the session starts, each participant receives a six digit code by email and has
to type it into the platform. Whoever is not actually in the session does not have the code, which
is why this prevents the fraud instead of detecting it afterwards.

The code is stored hashed, attempts are capped, and it expires.

> **Decision for you.** What happens when somebody does not confirm. My proposal: the session ends
> as `UNVERIFIED`, **the tutor does not earn credits**, the student is refunded, and the audit is
> notified. Earned credits are the ones that back a recognition request, so granting them without
> proof of presence would empty the mechanism of meaning. The harsher alternative, treating it as a
> no show, punishes somebody whose email simply did not arrive.

### `sessions.whiteboards`

## `wallet`

Credits: where they came from, when they die, and a history that cannot be rewritten.

### `wallet.credit_accounts`

```
id           uuid          PK
tenant_id    varchar(32)   NOT NULL
user_id      uuid          NOT NULL
created_at   timestamptz   NOT NULL DEFAULT now()

UNIQUE (tenant_id, user_id)
```

No balance column. The balance is the sum of what is left in the groups below.

### `wallet.credit_lots`

Credits arrive in groups, because the group is what carries the origin and the expiry.

```
id                 uuid          PK
tenant_id          varchar(32)   NOT NULL
account_id         uuid          NOT NULL REFERENCES wallet.credit_accounts(id)
credit_type        varchar(16)   NOT NULL   -- SEED | ALLOCATED | EARNED | PURCHASED
original_amount    integer       NOT NULL
remaining_amount   integer       NOT NULL
expires_at         timestamptz              -- only for SEED and ALLOCATED
expiry_notice_sent_at timestamptz            -- when the advance expiry notice was published
source_type        varchar(24)   NOT NULL   -- POLICY | SESSION | PURCHASE | REFUND
source_id          uuid
created_at         timestamptz   NOT NULL DEFAULT now()

CHECK (credit_type IN ('SEED','ALLOCATED','EARNED','PURCHASED'))
CHECK (original_amount > 0)
CHECK (remaining_amount BETWEEN 0 AND original_amount)
CHECK ((expires_at IS NULL) = (credit_type IN ('EARNED','PURCHASED')))
INDEX (tenant_id, account_id, expires_at) WHERE remaining_amount > 0
INDEX (tenant_id, expires_at) WHERE remaining_amount > 0 AND expiry_notice_sent_at IS NULL
```

The last `CHECK` is the rule of the product written where it cannot be broken: only what the
university grants expires. What you earned and what you paid for are yours.

Wallet records when it publishes the one advance expiry notice for a group. This marker makes
repeated daily job runs idempotent without changing the immutable credit movement history.

Spending takes from the group closest to expiring. A refund returns the credits to the group they
came from, with the expiry they had, which is why a refund is not simply "add credits back".

### `wallet.ledger_entries`

Every movement, in order, immutable.

```
id               uuid          PK
tenant_id        varchar(32)   NOT NULL
account_id       uuid          NOT NULL REFERENCES wallet.credit_accounts(id)
lot_id           uuid          REFERENCES wallet.credit_lots(id)
sequence_number  bigint        NOT NULL
direction        varchar(8)    NOT NULL   -- DEBIT | CREDIT
amount           integer       NOT NULL
reason           varchar(32)   NOT NULL   -- GRANT | BOOKING_CHARGE | BOOKING_REFUND |
                                          -- SESSION_EARNING | EXPIRY | PURCHASE |
                                          -- CAMPUS_BENEFIT_REDEMPTION |
                                          -- INCOMING_STUDENT_DONATION | ADJUSTMENT
reference_type   varchar(40)              -- BOOKING | SESSION | PURCHASE | POLICY |
                                          -- CAMPUS_BENEFIT_REDEMPTION |
                                          -- INCOMING_STUDENT_DONATION
reference_id     uuid
previous_hash    varchar(64)
entry_hash       varchar(64)   NOT NULL
occurred_at      timestamptz   NOT NULL DEFAULT now()

UNIQUE (tenant_id, sequence_number)
CHECK  (amount > 0)
CHECK  (direction IN ('DEBIT','CREDIT'))
INDEX  (tenant_id, account_id, occurred_at DESC)
```

Append only, enforced by a trigger that rejects `UPDATE` and `DELETE`. A correction is a new entry
with reason `ADJUSTMENT`; nothing is ever edited.

`entry_hash` covers the entry's own fields plus `previous_hash`, chained per university. Changing a
row behind the application's back breaks the chain from that point on, and a verification job finds
it. `sequence_number` is assigned by the application inside the transaction, not by a sequence,
because a sequence leaves gaps after a rollback and a gap looks exactly like a deleted row.

### `wallet.campus_benefits`

Benefits a university coordinator makes available for redemption with earned credits.

```
id             uuid          PK
tenant_id      varchar(32)   NOT NULL
name           varchar(120)  NOT NULL
description    varchar(500)  NOT NULL
credits_cost   integer       NOT NULL
active         boolean       NOT NULL DEFAULT true
created_at     timestamptz   NOT NULL DEFAULT now()
updated_at     timestamptz   NOT NULL DEFAULT now()

CHECK (credits_cost > 0)
INDEX (tenant_id, name) WHERE active = true
```

A benefit is deactivated rather than deleted so past redemption receipts remain meaningful. Its
name and cost are also copied to the credit-use record at redemption time.

### `wallet.credit_uses`

Confirmed redemptions and donations. The incoming-student pool is a projection of donation rows,
not a mutable balance that could drift from its history.

```
id               uuid          PK
tenant_id        varchar(32)   NOT NULL
student_id       uuid          NOT NULL
kind             varchar(32)   NOT NULL  -- CAMPUS_BENEFIT_REDEMPTION | INCOMING_STUDENT_DONATION
benefit_id       uuid          REFERENCES wallet.campus_benefits(id)
benefit_name     varchar(120)            -- snapshot for the redemption receipt
credits          integer       NOT NULL
idempotency_key  varchar(64)   NOT NULL
created_at       timestamptz   NOT NULL DEFAULT now()

UNIQUE (tenant_id, student_id, idempotency_key)
CHECK (credits > 0)
CHECK (redemption has benefit_id and benefit_name; donation has neither)
INDEX (tenant_id, created_at) WHERE kind = 'INCOMING_STUDENT_DONATION'
INDEX (tenant_id, student_id, created_at DESC)
```

Only remaining `EARNED` lots can be redeemed or donated. Each debit references this record in the

### `wallet.credit_use_confirmations`

Short-lived, student-scoped challenges that require an explicit second request before an
irreversible redemption or donation is accepted.

```
id            uuid          PK
tenant_id     varchar(32)   NOT NULL
student_id    uuid          NOT NULL
kind          varchar(32)   NOT NULL
benefit_id    uuid          REFERENCES wallet.campus_benefits(id)

## `reputation`

### `reputation.ratings`

```
id                 uuid          PK
tenant_id          varchar(32)   NOT NULL
session_id         uuid          NOT NULL
rated_by           uuid          NOT NULL
rated_user         uuid          NOT NULL
direction          varchar(24)   NOT NULL   -- STUDENT_TO_TUTOR | TUTOR_TO_STUDENT
stars              smallint                 -- only STUDENT_TO_TUTOR

comment            varchar(500)

```

The two directions ask different questions. A student says how good the tutoring was; a tutor

and not a score.

### `reputation.rating_tags`

```

### `reputation.rating_windows`

The completed sessions that can still be rated: one row per session, opened when reputation hears
`SessionCompleted`. It is not an opinion and nobody writes it through an endpoint.

```
tenant_id          varchar(32)   NOT NULL
session_id         uuid          NOT NULL
tutor_id           uuid          NOT NULL
student_id         uuid          NOT NULL
catalog_item_id    uuid          NOT NULL
opened_at          timestamptz   NOT NULL

PRIMARY KEY (tenant_id, session_id)
```

It exists because reputation may not ask `sessions` anything to rate: a rating arrives with a
session id and nothing else, and four things must be known at that moment. Whether the session
completed (no row, no rating, which is also why another university's session is a 404); who the
tutor and the student were, to refuse a stranger and to tell which direction the caller rates; and
which skill it was about, because a standing is per skill and the rating itself has no column for
it. The row holds exactly that, copied from the event.

It is also what makes `SessionCompleted` idempotent: the row is written in the same transaction
that counts the session in `tutor_standing.sessions_taught`, so finding it means the session was
already counted. Its primary key is the backstop, and whoever rates takes a lock on it so two
ratings of one session cannot both pass the check that it was not rated.

A projection, rebuilt from ratings. Never the source of truth.

## `audit`

### `audit.activity_log`

```
id             uuid          PK
tenant_id      varchar(32)   NOT NULL
actor_id       uuid
actor_role     varchar(16)   NOT NULL
action         varchar(64)   NOT NULL
resource_type  varchar(32)   NOT NULL
resource_id    uuid
metadata       jsonb
occurred_at    timestamptz   NOT NULL DEFAULT now()

INDEX (tenant_id, occurred_at DESC)
INDEX (tenant_id, resource_type, resource_id)
```

Append only, like the ledger, and for the same reason: it is what a decision is defended with.

**How the database refuses a change.** A `BEFORE UPDATE OR DELETE` row trigger,
`tr_activity_log_append_only`, raises `audit.activity_log is append only`, and a `BEFORE TRUNCATE`
statement trigger, `tr_activity_log_no_truncate`, does the same for `TRUNCATE`, which skips row
triggers. Both call `audit.reject_activity_log_change()`, the counterpart of
`wallet.reject_ledger_change()`. The refusal does not depend on the application, so somebody with a
`psql` prompt is refused too. A correction is a new row. The trigger can be dropped by whoever owns
the table, so it stops accidents and the application, not an administrator of the database: telling
an alteration apart is the pending scenario of US48, which needs the rows chained.

**What the columns hold.**

- `actor_id` is `NULL` when nobody is named: the system closing a session, or a decision whose event
  does not say which coordinator took it.
- `actor_role` is `STUDENT`, `TUTOR`, `COORDINATOR`, `SYSTEM`, or `UNKNOWN` for somebody who claimed
  to be a person the university does not know.
- `action` is what happened, in upper case, with the outcome in the name when there is one
  (`RECOGNITION_APPROVED`, `RECOGNITION_REJECTED`). `AUDIT_LOG_ACCESS_DENIED` is a refused attempt
  to read the log.
- `resource_type` and `resource_id` say what it happened to: `BOOKING`, `SESSION`, `WALLET` (the
  account of the person), `CATALOG_ITEM`, `VALIDATION_REQUEST`, `RECOGNITION_REQUEST`, `AUDIT_LOG`,
  `ANOMALY` (an alert, with `ANOMALY_DISMISSED` as its action).
- `metadata` is a flat object of strings that describes the fact: the other people involved, the
  amount, whether it was late. **It never holds an email address, a link or a code, nor the free
  text of a reason.**
- `occurred_at` is the moment the event says it happened, not the moment it was written.

### `audit.anomalies`

```
id             uuid          PK
tenant_id      varchar(32)   NOT NULL
kind           varchar(32)   NOT NULL   -- REPEATED_PAIR | UNUSUAL_FREQUENCY |
                                        -- SHORT_DURATION | FAILED_PRESENCE | NO_BOARD_ACTIVITY
subject_id     uuid          NOT NULL
severity       varchar(8)    NOT NULL   -- LOW | MEDIUM | HIGH
detail         jsonb
status         varchar(16)   NOT NULL   -- OPEN | DISMISSED | CONFIRMED
resolved_by    uuid
resolved_at    timestamptz
resolution_reason varchar(500)
detected_at    timestamptz   NOT NULL DEFAULT now()

CHECK (status IN ('OPEN','DISMISSED','CONFIRMED'))
CHECK (status = 'OPEN' OR (resolved_by IS NOT NULL AND resolved_at IS NOT NULL))
CHECK (status <> 'DISMISSED' OR resolution_reason IS NOT NULL)
INDEX (tenant_id, status, severity)
```

**`resolution_reason` was added in US47.** The first version of the model had `resolved_by` and
`resolved_at` and nowhere to keep why an alert was dismissed, which is the one thing a coordinator
is asked for when they do it. It is the free text of the decision, so it stays here and is not
copied to the activity log, as the reason of a validation or of a recognition is not. The two extra
checks make the table refuse what the application already does: a closed alert always says who and
when, and a dismissed one always says why. `kind` and `severity` are checked against the values
above too.

`subject_id` is the tutor whose credits the pattern puts in question, in every kind. The other
people involved and the figures that made it an anomaly are in `detail`, a flat object of strings
that holds identifiers and numbers only (`tutorId`, `studentId`, `unconfirmedUserIds`, `sessions`,
`bookedMinutes` and so on), never an address, a name or a reason.

An alert raised by one session (`FAILED_PRESENCE`, `SHORT_DURATION`) has a derived `id`, a name based
UUID of the university, the kind and the session, so the primary key is what makes one event
delivered twice produce one alert. The ones that come from a period (`REPEATED_PAIR`) have a random
`id`.

### `audit.anomaly_sessions`

```
anomaly_id   uuid          NOT NULL REFERENCES audit.anomalies(id)
session_id   uuid          NOT NULL
tenant_id    varchar(32)   NOT NULL

PRIMARY KEY (anomaly_id, session_id)
INDEX (tenant_id, session_id)
```

The coordinator sees these when reviewing a recognition request, which is the moment they matter.
The index is not in the first version of the model: recognition asks which open alerts a set of
sessions has, which is a lookup by session and not by anomaly.

credits             integer       NOT NULL
amount              numeric(10,2) NOT NULL
currency            varchar(3)    NOT NULL DEFAULT 'PEN'

## Counts

Twelve modules, twelve schemas, forty one tables. No table exists without a flow that needs it, and
no flow from the session is left without tables. `diagrams/schema-overview.png` shows all of them on
one page, drawn from `diagrams/schema-overview.puml`: a solid line is a foreign key inside a schema,
a dashed one a reference by uuid, and none crosses a schema. The diagram predates the two auxiliary
tables of `analytics` (`counted_events` and `active_student_days`), which are not counted above.
